# OKD → `mgmt-control` + `mgmt-workload` migration

Replace the 3-node OKD compact cluster with two purpose-built kubeadm clusters in the DevOps VPC. Drops OKD entirely. ~5-6 hour single-window operation.

## Goal

| Before | After |
|---|---|
| OKD compact 3-node (3 × 24 GiB = 72 GiB) hosts ArgoCD + argo-workflows + jenkins + OpenShift's whole operator zoo | **`mgmt-control`** (3 × 8-12 GiB) hosts ArgoCD SRE/DevOps, **Argo Workflows**, **Jenkins**, Crossplane, **Backstage** (the OpenShift-console replacement) |
| Single failure domain — OKD outage = GitOps stops | **`mgmt-workload`** (3 × 8-12 GiB) hosts **ARC controller + runners** + future ephemeral workloads |
| OpenShift-specific quirks: SCCs, Routes, OperatorHub | Pure kubeadm everywhere; consistent with mgmt-forge / mgmt-storage / mgmt-observability |
| Memory commitment 72 GiB | Memory commitment **48-72 GiB** depending on sizing; net 0 to −24 GiB savings |

### Service placement clarified

| Service | Lives on | Why |
|---|---|---|
| **ArgoCD SRE** | mgmt-control | GitOps controller — durable; can't move with the cluster |
| **ArgoCD DevOps** | mgmt-control | Same reasoning |
| **Argo Workflows** | mgmt-control | Workflow engine for platform jobs; stable runtime state on durable plane |
| **Jenkins** | mgmt-control | KEPT — moves over from OKD via the same Helm chart at `cplanes/devops/jenkins/`. Demo workloads continue. |
| **Backstage** (developer portal — replaces OpenShift console) | mgmt-control | The "what's the UI for the platform" answer once OKD's console is gone |
| **Crossplane** | mgmt-control | Cross-cluster IaC; control-plane-shaped |
| **Keycloak** (identity) | stays on mgmt-forge | Migration to mgmt-control deferred; not blocking |
| **Vault** | stays on mgmt-forge | Same |
| **ARC controller + listeners** | mgmt-workload | Runner spawning = workload plane work |
| **ARC runners** (`arc-runners-trusted`, `arc-runners-untrusted`) | mgmt-workload | Bursty, ephemeral, untrusted PR-build code — isolation matters |
| **Pattern A baseline** (cert-mgr, ingress-nginx, ESO, MetalLB, trivy-operator) | both clusters | Per-cluster install via existing AppSets |

After migration: control plane (durable services) and workload plane (ephemeral/bursty) are isolated to separate kubeadm clusters. OKD-specific features that no longer exist are replaced 1:1 by GitOps content already in `cplanes/`.

## What you LOSE (be honest about this)

| Lost | Replacement / acceptance |
|---|---|
| **OperatorHub catalog** (one-click operator install) | Each operator added as Helm chart in `cplanes/<plane>/<service>/` |
| **OpenShift Routes** (auto-cert + edge termination) | `Ingress` + cert-manager; same effective UX |
| **OpenShift's built-in monitoring** (cluster-monitoring-operator) | Already covered by `mgmt-observability` (Prom/Graf/Alertmgr) |
| **OpenShift OAuth + console** | Replaced by Keycloak (on `mgmt-forge` until migrated) + ArgoCD UI |
| **SCCs** | Pod Security Admission + OPA Gatekeeper (planned in `cplanes/security/compliance/`) |
| **kubeadmin password / cluster CA / etcd state on OKD** | None — these get regenerated by the new clusters' bootstrap |
| **argo-workflows runtime state** (running workflows, archive history) | Demo data; accept loss. Jenkins + argo-workflows redeploy fresh on mgmt-control. |
| **OKD's bootstrap automation in `okd/`** | Stays committed; can be reused for "DR rehearsal" but not part of normal ops |

## Rollback

There's no clean rollback once OKD is destroyed — you'd need to reinstall OKD from scratch (`okd/site.yml` again). At that point, the kubeadm clusters are still functional regardless. So:

- **If migration fails partway through (before ArgoCD installed)**: rebuild OKD via `okd/site.yml`, abort migration, debug.
- **If ArgoCD on mgmt-control is up but Applications won't sync**: keep mgmt-control, debug Application-by-Application. Don't roll back.
- **If mgmt-workload fails to bootstrap**: it doesn't block the migration; retry mgmt-workload independently.

The most painful failure scenario is "OKD destroyed, mgmt-control bootstrap stuck" — at that point you have neither ArgoCD nor any way to recover except finishing the bootstrap or rebuilding OKD. Mitigation: run pre-flight checks (especially #1) thoroughly.

## Known pitfalls

1. **Phase 8 chicken-and-egg**: solved by step 4's `argocd_register=false` flag. If you forget it, kubeadm bootstrap will fail trying to register with a non-existent ArgoCD.

2. **CoreDNS still serving OKD records**: if you skip step 2, ArgoCD on mgmt-control will see DNS NXDOMAIN for `api.mgmt-control.engatwork.com` and fail to register itself. Always update CoreDNS BEFORE bootstrapping mgmt-control.

3. **MetalLB pool overlap**: OKD's API + ingress VIPs (10.10.2.50, .51) are pfSense HAProxy fronted, NOT MetalLB. mgmt-control's MetalLB pool of `.200-.210` and mgmt-workload's `.211-.220` don't overlap. Don't reuse `.50/.51` — those stay reserved on pfSense for any future re-OKD.

4. **ArgoCD UI cert warnings**: same self-signed cert issue we hit on OKD. cert-manager will issue a Vault PKI cert for the ArgoCD ingress (once `cplanes/security/ca-pki/` is wired). Until then, browser warnings persist — same workaround (incognito, trust CA in OS, etc.).

5. **`storage-repo-secret` and `cluster-secret.yaml` files**: these are gitignored. Re-create on mgmt-control if needed (most likely not — anonymous fetch on public repo). Confirm by running ESO test queries.

   ```bash
   vault auth enable -path=kubernetes-mgmt-control kubernetes
   vault write auth/kubernetes-mgmt-control/config \
       kubernetes_host="https://10.10.2.110:6443" \
       kubernetes_ca_cert=@<mgmt-control-ca.crt> \
       token_reviewer_jwt=@<reviewer-token>
   vault write auth/kubernetes-mgmt-control/role/forge-reader \
       bound_service_account_names=external-secrets \
       bound_service_account_namespaces=external-secrets \
       policies=forge-reader \
       ttl=1h

   # Same for mgmt-workload
   ```
